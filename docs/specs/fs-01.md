## Scope and architecture anchors

**Scope:** language-neutral facts, capabilities, registrations, variants, uncertainty, and compatible projections.

**Architecture changes:** generalize project metadata from one extractor to language/profile/extractor sets. Keep TS ASTs adapter-owned. Extend canonical snapshots and validation only for facts needed by this roadmap; retain existing import and behavior projections.

**Tasks:**

1. Add analysis profile/variant identity and capability records to snapshots and their identity digest.
2. Define typed framework bindings and route registrations with stable snapshot-scoped IDs rather than relying on route array indices for new features.
3. Separate page/navigation routes from HTTP endpoints. HTTP methods can be known, unrestricted by registration, unknown, or dispatch-dependent; do not substitute invented GET/ALL values for unknown methods.
4. Preserve raw route syntax plus a typed matcher representation: segments, converters/regex, precedence, conditions, prefix evidence, and variant. Unsupported matching is a gap, not a generic string comparison.
5. Support multi-site evidence for composed facts: registration, declaration, config, and handler can be in different files. Keep old first-occurrence provenance honest.
6. Add snapshot-local resource/config evidence only where needed. Every permitted witness is bound to content hash and canonical-root policy; no durable source archives.
7. Normalize adapter positions into the established source-range convention. Explicitly handle UTF-8 parser offsets, UTF-16 UI offsets, Unicode, line endings, and Python source encodings.
8. Keep candidates outside verified graph adjacency. Version storage/protocol/projection contracts as required; preserve old snapshots as readable limited-capability data or require reanalysis explicitly. Never backfill new facts as empty proven results.

**Tests:** serializer/validator round trips; dangling/duplicate IDs; wrong endpoint types; unsupported variants; multi-file provenance; malformed candidate promotion; UTF-8/UTF-16/CRLF fixtures; compatible and incompatible historical snapshots; unchanged old import/Impact results.

**Acceptance:** all new facts validate and open correct current evidence. Old supported repositories retain equivalent file dependencies and exact Impact. Generic algorithms contain no framework AST logic. Migration behavior is explicit and atomic.

**Deliverables:** contract specification, validators, compatibility projections, snapshot migration/reanalysis policy, capability presentation using current UI components, regression fixtures.

Implementation areas: lib/engine/types.ts, contract.ts, snapshot-identity.ts; lib/model/behavior.ts, validate.ts; lib/desktop/protocol.ts, projection.ts; lib/storage/types.ts, sqlite.ts. These are extension anchors, not permission to replace their architecture or remove current features.

Do not create v3 facts by default-filling v2 fields. Additive settings migrations, if actually needed, require their own transaction tests.
6. Add candidate/gap/capability projection using current UI components; keep the accepted layout. Use fixtures to assert that unknown method, unsupported matcher, stale hash and user assumptions stay visibly distinct.

## Executable verification contract

Shared new-record reason enum: `dynamic-expression`, `ambiguous-target`, `custom-resolver`, `unknown-origin`, `unknown-method`, `unsupported-syntax`, `unsupported-matcher`, `unsupported-encoding`, `missing-metadata`, `policy-denied`, `generated-code-unavailable`, `variant-not-selected`, `external-boundary`, `resource-limit`, `parser-unavailable`, `parse-error`, `candidate-overflow`, `config-cycle`, `rewrite-cycle`, `stale-evidence`. Preserve legacy gap representations through the compatibility reader rather than coercing them to an unrelated new reason. Version this enum with v3; unknown reasons are rejected at publication, not silently dropped. Additional implementation-discovered reasons require an explicit contract/spec change.

Witness shape reuses the existing hash-bound Site plus extractor identity/version, role (`declaration`, `registration`, `reference`, `configuration`, `framework-rule`) and variant. A source-derived relation requires permitted source/config witnesses and may include a pinned framework-rule witness; rule-only evidence cannot invent a handler declaration. Assumption records are separate local user inputs with revision and selected variant, not fake source Sites. Stable fact IDs include kind, normalized project-relative path, original-source range, variant ID and target semantic key where required; content/config hashes belong in evidence/cache identity, and timestamps never influence graph identity. Registration identity keeps duplicate registration occurrences distinct.

Create tests/framework-support/fs-01.test.ts and synthetic fixture records for F01-contract, F00-position only when this phase is authorized. Each table case asserts exact verified semantic facts and witnesses, candidates, typed gaps and forbidden guessed facts; missing oracle/tuple evidence fails qualification. Test deterministic repeated analysis and full/incremental equivalence. Unit-only syntax success never grants a framework badge.

Run the new suite with `node --test tests/framework-support/fs-01.test.ts`; the file does not exist in FS-00. Use explicit tuple/profile fixture filters in the future runner and report every target, including skipped/unavailable cases. Developer-only oracle generation is a separate opt-in command documented with pinned tools, fixture hash and output hash; never invoke an oracle during normal analysis.

Required phase-specific assertions: Round-trip v2 unchanged; v3 JSON round-trip and deterministic IDs; invalid references/enums/ranges fail; interrupted publication keeps old generation; existing file dependency/Impact goldens unchanged.

Run existing `pnpm test`, `pnpm exec tsc --noEmit` after Next typegen, `pnpm lint`, and relevant Rust/asset/packaged checks from the [baseline ledger](../fs-00/regression-baseline.md). Refresh/storage/evidence correctness is required in each phase, not deferred to FS-09. Rebuild staged engine resources for package changes only within the authorized development phase.

## Acceptance and delivery checklist

- Scope-specific assertions above and inherited plan acceptance pass with retained logs; every manifest capability is qualified/partial/unsupported/blocked from its own evidence.
- Relevant fixture/oracle records contain exact tuple, selected variants, extractor version, source/output hashes, bounded resource outcomes and missing-proof reasons. No guessed edge enters verified projection.
- Existing dependencies, structural Impact, evidence/staleness, TS/JS support, Windows behavior, frozen Laya and optional explanation consent remain intact.
- Deliver phase code, tests, approved dependency/resource/license changes if needed, per-pattern qualification ledger, budget measurements, and updated limitations. No automatic commit, push or release publication.
- Remaining failures are blockers for their claimed capability; record partial scope explicitly. Do not silently widen budgets or version claims to complete the phase.
