# FS-01 shared contract and compatibility

Implemented snapshot format: **v3**. Historical v2 remains a distinct validated type and reader. Parser schema4, engine adapter version4, and IPC envelope version1 are independent versions. No future framework tuple became qualified.

## Canonical shared data

`CodeSnapshot.analysis` holds project language/extractor/profile sets, protected resource dimensions/hashes, profiles, analysis variants, qualifications, capability assessments, route registrations, framework bindings, candidates, typed gaps and explicit user assumptions. Existing `files`, `relationships`, `routes` and `behavior` remain their compatibility projections. Import adjacency, type-only flags, first-occurrence import evidence, file degrees, structural Impact, legacy route indices and existing direct-call traces keep their meaning.

`lib/model/framework.ts` is the language-neutral type/identity contract; `framework-validate.ts` validates its records without parser ASTs, filesystem access, providers or graph traversal. `lib/engine/contract.ts` composes it with the retained legacy content validator. Collections reject missing/unknown fields, duplicate/colliding IDs, broken references, wrong endpoint types, invalid variants, invalid ranges/hashes, unknown enum values and candidate promotion into import IDs. Source owner/occurrence scope and target declaration witnesses are required for verified bindings. HTTP candidates can target only HTTP registrations.

Profiles identify project/resolver/semantics; variants identify profile/environment/platform/ordered conditions and config witnesses. Capability IDs include tuple/capability/profile/variant. Qualified assessments require a matching complete positive/negative/Windows ledger, exact extractor version and output hashes. These gates are contract validation, not an automatic framework qualification service. The fresh TS adapter publishes `legacy-observations` with partial `existing-ts-js-observations` assessments; it does not fabricate completed version/pattern qualification.

Registrations have source-scoped IDs, handler declaration IDs, selected variant, raw pattern, explicit method state, typed matcher, optional precedence, conditions, prefix witnesses and all supporting sites. Page/navigation records have no HTTP method. HTTP methods support known tokens, registration-unrestricted `all`, unknown and dispatch-dependent states; the latter two retain an `unknown-method` gap. Supported matchers specify segments/converter domains, slash/case/decoding policy; unsupported matching requires a linked gap. Arbitrary regex is not interpreted. Legacy methods/patterns remain visible unchanged; their new matcher is explicitly unsupported until a later qualified extractor supplies semantics. Legacy `ALL` is conservatively unknown in the new projection.

`factId` uses kind, normalized relative path, original half-open range, variant and target key. Legacy registration target keys include raw pattern and method to distinguish shared-source registrations. IDs exclude hashes/timestamps; snapshot identity still includes **every** analysis value through existing canonical key sorting. Hash/variant/config changes therefore invalidate cached snapshot identity without redefining file candidate IDs or model features.

## Evidence and source positions

Source witnesses retain hash-bound `Site`, extractor version, role and variant. Framework-rule witnesses carry a pinned tuple/rule identity and cannot establish a source relationship alone. User origin/service mappings are separate assumption records with revision and user provenance; no fake source witness or verified deployment fact is created.

Resources retain path, raw-byte hash/count, UTF-16 length, line count, encoding and read purpose, not source text. Initial extra metadata witnesses are narrowly named first-party package/tsconfig/jsconfig JSON; future formats/read-policy extensions remain FS-02 or later work. Dependency/generated/dot-directory and sensitive evidence reads remain denied by the protected reader. Existing TS decoding is explicitly `legacy-decoded`; it is not relabelled strict UTF-8.

`normalizeRange` converts explicitly declared UTF-8 byte boundaries or UTF-16 offsets to original-text half-open UTF-16 positions. It rejects interior UTF-8 boundaries, split surrogate pairs, invalid units and out-of-range positions. CRLF, BOM, emoji and combining characters are preserved. `decodeSource` adds strict UTF-8/ASCII and bounded Python cookie handling for future adapters; no Python parser/runtime is installed or invoked.

Schema validation checks range dimensions and matching recorded hashes. It cannot prove semantic extraction or actual text line boundaries from a hash alone. `readWitnessEvidence` additionally reopens protected current bytes, checks the hash and actual coordinates, and refuses stale/unavailable/mismatched evidence. Every composed witness is checked separately; one current site does not certify the whole relationship. The diagnostics panel opens each source/config witness through the existing native evidence command, with current/stale/unavailable states and original excerpts. Framework rules remain labelled rules, and assumptions remain labelled user input.

## Format migration, retention and publication

`inspectSnapshot` returns either current-format v3 or `reanalysis-required` v2. It never adds v3 fields to v2. `validateSnapshot`/current graph operations accept v3 only; `validateLegacySnapshot` and legacy serializers preserve valid v2 content. Unknown formats fail closed. A retained historical format is not evidence that files are currently unchanged.

SQLite keeps its existing schema and current snapshot slot. Failed/cancelled/interrupted reanalysis retains the old payload; publication and job completion remain one transaction. To protect against a v2 writer replacing that slot after downgrade, publication also retains the last v2 and last v3 format payloads in existing repository settings keys `retained-snapshot-v2` and `retained-snapshot-v3`. These are canonical fact snapshots, not source archives. Both retention writes roll back with publication failure. `loadRetained` permits explicit format inspection and never activates a backup automatically. A newer primary format is protected from overwrite by this version. Forgetting cascades all copies through the existing foreign key.

Each payload remains capped at 31 MiB. Retention adds at most two copies of 31 MiB each, plus the existing current slot; this is a bounded local disk cost, with no additional source-read or IPC budget. The v3 copy survives an actual historical v2 writer in the recorded experiment. No general unbounded history/archive service or new database migration is introduced.

Analysis/reopen requests pin `snapshotVersion: 3` in the existing v1 envelope; replies must carry a valid v3 snapshot. New workers reject missing/old pins before analysis; historical workers reject the new field before analysis. The framing layer exits 2 on rejected input without echoing unsafe request data. The Windows host sends the pin and accepts v3, while stage metadata advertises v3 and historical v2. Publication cannot proceed through a mixed worker/client contract. Existing release resources remain v2 and self-compatible; they were used as the historical oracle, not upgraded or called a new release.

## Explicit limits

No resolver/config interpreter, new language parser, framework extractor, navigation semantics, native bridge analysis, origin discovery or cross-stack linking was added. No new framework support badge, native runtime guarantee or installed MSI/NSIS qualification follows from FS-01. Candidates remain outside verified import adjacency. Laya artifact/features/candidates and optional explanation consent/digest/cache behavior are unchanged. New diagnostics use the completed UI's existing surface; no layout redesign was performed.
